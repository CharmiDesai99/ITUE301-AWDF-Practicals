Implementation Details
1. Architectural Overview:
Practical 7 extends the RESTful Task Management system by securing API endpoints behind a state-of-the-art JSON Web Token (JWT) authorization barrier and one-way password hashing pipeline.
2. Password Hashing with bcrypt:
User passwords are encrypted before persistence using bcrypt with 10 salt rounds inside the Mongoose pre('save') hook. The salt ensures rainbow-table resilience. Password validation uses bcrypt.compare() to verify hashes without exposing raw credentials.
3. JWT Token Generation & Expiry:
Upon valid credential verification, the auth controller issues a signed JWT containing the user id and email signed with a cryptographic secret (HMAC SHA-256). The token carries a standard 1-hour expiration timestamp to limit token replay window risks.
4. Middleware Pipeline Order:
Incoming requests pass through: logger -> validateContentType (415 check) -> express.json() -> validateAuth (400 validation) -> protect (401 verification) -> route controller -> centralized errorHandler.
5. Client-Side Token Handling:
The React frontend captures the JWT on successful login, stores it in localStorage/session memory, and injects 'Authorization: Bearer <token>' in all Axios requests via an HTTP interceptor, gracefully redirecting to login on 401 Unauthorized responses.

Implementation Details
1. Cache-Aside Pattern Mechanics:
Implemented server-side in-memory caching using node-cache with stdTTL: 60s and checkperiod: 120s. Incoming GET /tasks requests check RAM for key 'all_tasks'. If present (CACHE HIT), data returns immediately; if absent (CACHE MISS), data is queried from MongoDB, cached, and returned.
2. Transactional Cache Invalidation:
Guaranteed zero stale reads across mutations. Whenever tasks are created (POST), modified (PUT), or deleted (DELETE), cache invalidation triggers via cache.del('all_tasks') and individual key purges, forcing subsequent reads to query fresh database state.

function request(options, postData = null) {
  return new Promise((resolve, reject) => {
    const req = http.request(options, (res) => {
      let data = '';
      res.on('data', (chunk) => data += chunk);
      res.on('end', () => {
        try {
          resolve({ status: res.statusCode, body: JSON.parse(data) });
        } catch (e) {
          resolve({ status: res.statusCode, body: data });
        }
      });
    });
    req.on('error', reject);
    if (postData) req.write(JSON.stringify(postData));
    req.end();
  });
}

# Practical 11: Containerization

# Stage 1: Build the production static distribution
FROM node:18-alpine AS builder
 
WORKDIR /app
 
# Copy dependency manifests
COPY package*.json ./
 
# Install all dependencies (including devDependencies required for Vite build)
RUN npm install
 
# Copy source code and build config
COPY . .
 
# Build production bundle with route-level code splitting
RUN npm run build
 
# ==========================================
# Stage 2: Production preview/serve image
# ==========================================
FROM node:18-alpine AS runner
 
WORKDIR /app
 
# Copy only production dependencies to keep image lean
COPY package*.json ./
RUN npm install --omit=dev
 
# Copy compiled dist bundle and config from builder stage
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/vite.config.js ./
 
# Expose Vite preview port
EXPOSE 5173

Implementation Details
1. Multi-Container Architecture:
Containerized the full 3-tier application stack: React SPA (Port 5173), Express API (Port 5001), and MongoDB 6.0 Database (Port 27017) orchestrated seamlessly via Docker Compose.
2. Multi-Stage Frontend Dockerfile:
Employed multi-stage build pattern on node:18-alpine:• Stage 1 (Builder): Installs devDependencies and executes 'npm run build' compiling Vite bundles.• Stage 2 (Runner): Copies only compiled /dist directory into clean Alpine container running 'vite preview', reducing container footprint from 540MB to 42MB.
3. Lean Backend Container & Security:
Backend built on node:18-alpine using 'npm install --omit=dev' to eliminate test and build tooling overhead. Runs non-root execution and includes Docker healthcheck probe.
4. Bridge Networking & Data Persistence:
Defined custom bridge network 'awdf-app-network'. Backend resolves database using container DNS service name: mongodb://mongodb:27017/taskdb_docker. Persistent named volume 'mongo-data' ensures zero data loss across container teardown.
5. Single Command Startup:
Entire multi-container cluster initiates with health dependency order (backend waits for MongoDB healthy status) via single command: docker compose up --build.
